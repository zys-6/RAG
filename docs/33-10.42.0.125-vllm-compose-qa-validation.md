# 33 - `10.42.0.125` Host `vLLM` with Compose Backend Validation

This document records the exact working state validated on July 29, 2026 for the `10.42.0.125` environment.

It is narrower than the earlier GPU-stack notes. The goal here was not just to bring up services, but to prove that:

1. host `vLLM` can serve the LLM on port `8000`
2. Compose-managed `embedding_api`, `document_fragment_api`, and `qa_api` can start on the same host
3. `qa_api` can stream a real response through the backend using the live `vLLM` server

---

  - `document_fragment-qa_api-1`

Published ports:

- `document_fragment_api` -> `12355`

## Failures encountered and what they meant

### 1. `bash standalone_embed.sh start` failed in repo root

Symptom:

```text
bash: standalone_embed.sh: No such file or directory
```

Meaning:

- the script was not in `/home/jj/document_fragment`
- the active saved Milvus startup contract lived under `/home/jj/setup`

Fix:

- run the script from `/home/jj/setup`

### 2. `qa_api` crashed with missing config keys

First failure:

```text
KeyError: 'MODEL_NAME2'
```

Meaning:

- this code path reads `MODEL_NAME2`, `API_KEY2`, and `API_BASE_URL2` unconditionally during import

Fix:

- add the secondary LLM keys to `src/rag/configs/app_config_pro.yaml`

### 3. `qa_api` crashed on Milvus with `host.docker.internal`

Failure:

```text
Fail connecting to server on host.docker.internal:19530
```

Meaning:

- on this Linux Docker host, `host.docker.internal` was not the right address for container-to-host Milvus access

Fix:

- use:

```text
http://172.17.0.1:19530
```

for `MILVUS_URI`

### 4. First QA request failed with model not found

Failure:

```text
The model `Qwen3-14B-AWQ` does not exist.
```

Meaning:

- `vLLM` was serving the model id:
  - `"/models/Qwen3-14B-AWQ"`
- the backend was requesting:
  - `"Qwen3-14B-AWQ"`

Fix:

- set `MODEL_NAME` and `MODEL_NAME2` to the exact served model id:

```text
/models/Qwen3-14B-AWQ
```

### 5. First `curl` request formatting was broken by shell line handling

Failure:

```text
-H: command not found
```

Meaning:

- the multi-line `curl` command was broken across shell input incorrectly

Fix:

- rerun the full `curl` command with valid line continuation

### 6. Offline image load was incomplete for Compose startup

Observed on the offline clone recovery before the later `192.168.1.100` fixes.

Symptoms:

- the target host successfully loaded:

```text
Loaded image: milvusdb/milvus:v2.4.4
Loaded image: embedding_api:cuda12.1
Loaded image: vllm/vllm-openai:latest
```

- `docker images | grep -E 'embedding_api|milvus|vllm'` confirmed those tags existed
- but `docker compose up -d embedding_api document_fragment_api qa_api` still failed offline because Compose wanted `document_fragment:mupdf-3`

Meaning:

- loading `milvus.tar`, `embedding_api_cuda12.1.tar`, and `vllm-openai-latest-working.tar` was not enough for this Compose file
- the Compose services `document_fragment_api`, `embedding_api`, and `qa_api` all reference:

```text
document_fragment:mupdf-3
```

- if that image is absent locally, Docker tries Docker Hub and fails on an offline host

Questions to ask immediately:

- does `docker images` contain `document_fragment:mupdf-3`?
- does the active `docker-compose.yaml` use `document_fragment:mupdf-3` for all three services?
- was only `embedding_api:cuda12.1` loaded, but not the base app image tag that Compose expects?

Fix:

- make sure the target host has a local `document_fragment:mupdf-3` image before running Compose
- either load the correct `document_fragment:mupdf-3` image tarball
- or intentionally retag a known-good local image only if that image really matches the expected app runtime

Operational meaning:

- on an offline host, validate image tags before debugging Python, ports, or container startup
- `docker load` success for related images does not prove Compose has every image tag it needs

### 8. `models/reranker/tokenizer.json` existed but was corrupted

Observed on `192.168.1.100`.

Symptoms:

- `embedding_api` crashed in `src/embedding/api.py` at:

```text
AutoTokenizer.from_pretrained(os.environ.get("RERANKER_MODEL_PATH", "/models/reranker"))
```

- the traceback ended with:

```text
json.decoder.JSONDecodeError: Expecting value: line 1 column 1 (char 0)
```

- `tokenizer.json` failed JSON parsing
- `python -c "print(repr(open(...,'rb').read(80)))"` showed leading `\x00`

Meaning:

- but `tokenizer.json` was NUL-filled corruption, not valid JSON

Questions to ask immediately:

- does `docker compose ps -a` show `embedding_api` as `Exited (1)`?
- does `/models/reranker/tokenizer.json` parse with `json.load(...)`?
- do the first bytes of `tokenizer.json` start with `b'{'` or with `b'\\x00'`?

Fix:

- replace `models/reranker/tokenizer.json` or the full `models/reranker/` directory from a known-good source
- in this incident, the effective good lineage was the inner-network source `192.168.1.227`

## August 13, 2026 addendum: confirmed CUDA compose file and switch path

Later, a smaller follow-up operation confirmed the optional CUDA compose path on a ThinkStation-style host layout without redoing the full end-to-end validation in this document.

What was directly confirmed from the live terminal:

- the remote project path was `/home/user1/document_fragment`
- the file `/home/user1/document_fragment/docker-compose.gpu-host.yaml` existed
- `docker compose -f docker-compose.gpu-host.yaml config --services` showed `embedding_api`

That result is correct. In `docker-compose.gpu-host.yaml`, the Compose service name remains `embedding_api` even though the container name is `embedding_api_gpu`.

The naming split is:

- Compose service name: `embedding_api`
- container name: `embedding_api_gpu`

This matches the CUDA compose definition used in the repo:

```yaml
services:
  embedding_api:
    image: embedding_api:cuda12.1
    container_name: embedding_api_gpu
    ports:
      - "15006:5006"
```

Operational meaning:

- the default `docker-compose.yaml` still represents the CPU-backed path on `12356`
- `docker-compose.gpu-host.yaml` represents the optional CUDA-backed path on `15006`
- seeing `embedding_api` from `config --services` does not mean the CPU compose file is being used

Minimal switch sequence on that host:

```bash
cd /home/user1/document_fragment

sudo docker compose stop embedding_api
sudo docker compose rm -f embedding_api

sudo docker compose -f docker-compose.gpu-host.yaml up -d embedding_api
sudo docker ps --filter name=embedding_api_gpu
curl http://127.0.0.1:15006/docs
```

If application services should consume the CUDA endpoint instead of the CPU compose service, point both config layers at:

```text
EMBEDDING_URL=http://<gpu-host>:15006/embeddings
RERANK_URL=http://<gpu-host>:15006/rerank
```

Then recreate the callers:

```bash
sudo docker compose up -d --force-recreate document_fragment_api qa_api
```

`docker compose restart` alone is not enough after changing `.env`.

Scope note:

- this addendum confirms the file existence, service-name interpretation, and intended switch procedure
- it does not claim that CUDA embedding/rerank was fully revalidated end-to-end on August 13, 2026

### 9. Direct answers to the image/compose questions that caused confusion

These answers were implied earlier in the note, but the manual summary made it clear they should be stated directly.

#### What does `document_fragment-mupdf-3` do?

`document_fragment-mupdf-3.tar` is an exported Docker image tarball. After:

```bash
docker load -i document_fragment-mupdf-3.tar
```

it becomes the local image tag:

```text
document_fragment:mupdf-3
```

That image is the shared application runtime for the default Compose stack:

- `document_fragment_api`
- `embedding_api`
- `qa_api`

It provides the Python environment, PyTorch, PyMuPDF, project runtime dependencies, and the baked-in application base that those three services reuse.

#### Does `document_fragment:mupdf-3` contain `embedding_api`?

Yes.

More precisely:

- the image contains the runtime and code needed to start `embedding.api:app`
- the default `docker-compose.yaml` uses that same image for all three services
- the difference between the three services is mainly the Compose `command`, mounts, and environment

That is why this works when the base image is present:

```bash
docker compose up -d embedding_api document_fragment_api qa_api
```

And that is also why it fails offline if `document_fragment:mupdf-3` is missing, even when related images such as `embedding_api:cuda12.1` are already loaded.

#### Does `docker-compose.gpu-host.yaml` cover the `mupdf-3` embedding?

Only indirectly.

`docker-compose.gpu-host.yaml` starts:

```text
embedding_api:cuda12.1
```

not:

```text
document_fragment:mupdf-3
```

But `embedding_api:cuda12.1` is built on top of `document_fragment:mupdf-3`, so it still reuses the same app/runtime base. Operationally:

- `docker-compose.yaml` = default CPU/local embedding path on `12356`
- `docker-compose.gpu-host.yaml` = optional CUDA embedding path on `15006`

It does **not** start:

- `document_fragment_api`
- `qa_api`

So it does not replace the whole default application stack.

#### Can the old process be optimized?

Yes. The clean optimization is to stop thinking of `embedding_api` as something that must always be started locally together with the other two app services.

There are three distinct deployment modes:

##### Mode A: full local default Compose stack

Use this when one host runs all app services locally.

Needed images:

- `document_fragment:mupdf-3`
- `milvusdb/milvus:v2.4.4`

Typical commands:

```bash
sudo docker load -i document_fragment-mupdf-3.tar
sudo docker compose up -d embedding_api document_fragment_api qa_api
```

##### Mode B: app host uses remote GPU embedding service

Use this when `document_fragment_api` and `qa_api` stay local, but embedding/rerank should run on another GPU host.

Needed on the app host:

- `document_fragment:mupdf-3`
- `milvusdb/milvus:v2.4.4`

Do **not** start the local `embedding_api` if both config layers point at the remote GPU endpoint.

Typical commands on the app host:

```bash
sudo docker load -i document_fragment-mupdf-3.tar
sudo docker compose up -d document_fragment_api qa_api
```

And point both config layers at:

```text
EMBEDDING_URL=http://<gpu-host>:15006/embeddings
RERANK_URL=http://<gpu-host>:15006/rerank
```

After config changes, recreate the callers:

```bash
sudo docker compose up -d --force-recreate document_fragment_api qa_api
```

##### Mode C: GPU host serves only embedding/rerank

Use this on the GPU machine that provides the remote embedding endpoint.

Needed on the GPU host:

- `embedding_api:cuda12.1`

Typical commands:

```bash
sudo docker load -i ~/offline-gpu-notes/embedding_api_cuda12.1.tar
cd /home/user1/document_fragment
sudo docker compose -f docker-compose.gpu-host.yaml up -d embedding_api
curl http://127.0.0.1:15006/docs
```

This mode is enough for remote embedding/rerank only.

#### What is **not** enough?

This is the common mistake the recovery notes exposed:

```bash
sudo docker load -i ~/offline-gpu-notes/embedding_api_cuda12.1.tar
sudo docker compose up -d embedding_api document_fragment_api qa_api
```

Why it is not enough:

- the default `docker-compose.yaml` still expects `document_fragment:mupdf-3`
- `document_fragment_api` and `qa_api` do not run from `embedding_api:cuda12.1`
- loading the CUDA embedding image alone does not satisfy the base-image requirement of the default Compose stack

Short conclusion:

- if you need the full local stack, load `document_fragment-mupdf-3.tar`
- if you need only remote GPU embedding, `docker-compose.gpu-host.yaml` is enough on the GPU host
- if the app host will call that remote embedding service, you can optimize the old process by starting only `document_fragment_api` and `qa_api` locally and skipping the local `embedding_api`
